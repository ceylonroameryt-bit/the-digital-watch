Manchester Airports Group Data Breach: What Actually Happened, and Why It Matters

You saw the headline. Here’s what actually happened.

1. What Actually Happened

On 27 August 2026, Manchester Airports Group confirmed that it had suffered a cyber security incident.

If you only saw the headline, you could easily imagine something dramatic: airport systems offline, flights cancelled, check-in desks failing or perhaps even aviation systems being compromised.

None of that happened.

Manchester, London Stansted and East Midlands airports continued operating normally. According to Manchester Airports Group (MAG), the incident did not involve operational airport systems, and passenger safety and aviation security were never compromised.

The problem was elsewhere.

Customer data had been obtained.

Information connected with airport Wi-Fi registrations, car parking, Fast Track and lounge bookings was caught up in the incident. The affected information included email addresses, phone numbers, postcodes and vehicle registration numbers.

MAG says the affected system did not contain customers' bank or payment details. Later reporting put the number of affected people at approximately 8.7–8.8 million.

Then the story became much more interesting.

A cyber-extortion group calling itself FulcrumSec claimed responsibility and said it had obtained access using API credentials exposed in JavaScript on MAG's airport websites.

Normally, I would be very cautious about a statement like that. Criminal groups have obvious reasons to exaggerate what they have done.

But this particular claim was testable.

Security researcher Scott Helme tested it.

And he found the keys.

2. The Credentials Were Really There

Helme investigated the JavaScript being delivered by the Manchester, Stansted and East Midlands airport websites.

He eventually found three separate Iterable API credentials — one associated with each airport.

That was significant because FulcrumSec had specifically described the credentials as airport-specific.

Helme then used historical copies of the websites to work out how long they had been exposed. His investigation found:

  • East Midlands Airport: credential appearing from 23 June 2022
  • London Stansted Airport: credential appearing from 28 June 2022
  • Manchester Airport: credential appearing from 11 July 2022

The same respective values continued appearing in archived JavaScript until August 2026.

In other words, the exposure appears to have lasted for a little over four years.

There is an important distinction here.

That does not mean attackers had access for four years. We do not currently know when FulcrumSec first obtained the credentials. What we can say is that the credentials were publicly exposed during that period.

An exposure window and an intrusion window are not the same thing.

3. Is Exposing API Credentials in JavaScript Actually a Real-World Problem?

Very much so. And MAG is not an isolated example.

In March 2026, researchers Nurullah Demir, Yash Vekaria, Georgios Smaragdakis and Zakir Durumeric published research titled “Keys on Doormats: Exposed API Credentials on the Web.”

They examined approximately 10 million webpages looking specifically for exposed API credentials.

They identified:

1,748
Distinct Credentials
~10,000
Vulnerable Webpages
14
Service Providers

Some of those credentials were found on highly prominent websites, including sites belonging to major banks and technology organisations.

More importantly for the MAG case, the researchers found that many of the exposures originated from JavaScript environments. Historical analysis also showed that some credentials remained exposed for periods ranging from months to several years.

That makes the MAG situation much less unusual than it initially sounds. This isn't merely:

“One developer accidentally put a key in one website.”

There is a broader industry problem around secrets moving from supposedly protected development environments into frontend applications where anybody can inspect them.

4. Why Does Putting a Secret in JavaScript Matter?

Imagine an organisation has a room containing millions of customer records.

There is a lock on the door. Only authorised employees should have the key.

Now imagine somebody places a copy of that key inside a leaflet handed to everyone entering the building.

The room is still locked. The problem is that the thing protecting it isn't secret anymore.

The same principle applies here.

A modern website downloads JavaScript to your browser. If your browser receives that JavaScript, you can inspect it. So can I. So can a security researcher. And so can an attacker.

The Golden Rule of Frontend Architecture:

Anything delivered to the browser should be treated as observable by the user.

That doesn't mean API keys can never exist in client-side applications. Some APIs deliberately provide restricted client-side credentials.

The important questions are:

  • What can the key do?
  • Was it designed to be public?

5. Iterable Itself Warns Developers About This

This isn't a security rule invented after the MAG breach.

Iterable's own documentation distinguishes between client-side and server-side API credentials.

Server-side keys have substantially greater access. Iterable explicitly warns developers not to embed those server-side credentials inside client-side applications because they can potentially be used to access project data. That includes JavaScript and mobile applications.

Iterable provides more restricted client-side key types for browser applications. Modern client-side configurations can also use JWT authentication, adding another authentication layer rather than trusting possession of the API key alone.

This is important because it changes how we should understand the MAG incident. If Helme's analysis is correct, the issue wasn't simply:

“MAG used an API key.”

Using API keys is normal. The issue was potentially:

A credential intended to have server-side authority was exposed in an environment where anyone could retrieve it.

Those are very different things.

6. What Was the Airport Website Actually Doing with the Key?

This is one of the details I found most interesting.

You might assume the website needed powerful API access because it was performing some complicated customer-management function.

Helme examined the JavaScript responsible for the Iterable integration. The browser-side functionality appears to have been largely connected with marketing attribution and event tracking.

For example, the application could record that someone had arrived at a page through a particular marketing campaign. That's completely normal. Businesses need analytics. Marketing teams need to understand whether campaigns work.

The security question is whether the credential being used had far more authority than that relatively simple job required.

That brings us to one of the oldest principles in cybersecurity:

Principle of Least Privilege

Give a user, system or credential only the permissions necessary to perform its job. Nothing more. If a browser needs to submit a marketing event, its credential should not also provide access to functionality capable of retrieving or exporting large quantities of customer information.

7. We Have Seen the API Problem Before

MAG isn't the first major organisation where an API became central to a huge data incident:

T-MOBILE (2023) 37 Million Customer Accounts

In January 2023, T-Mobile disclosed that an attacker had been obtaining customer information through a single API without authorisation. The information included names, billing addresses, emails, phone numbers, birth dates, and account details. The attacker didn't need to compromise individual accounts — one API provided a path to information at enormous scale.

TRELLO / ATLASSIAN (2024) 15 Million Profile Correlations

An attacker obtained email addresses elsewhere and used Trello's REST API to match those addresses against public profile information. The API was doing what it was designed to do, but unauthenticated querying at scale created a privacy catastrophe. Atlassian changed the API to stop unauthenticated profile lookups by email.

Sometimes the API isn't broken. The assumption behind the API is broken.

OPTUS (2022) Follow-on Fraud & Identity Scams

Millions of Australian customers had identity details exposed via an API. The Australian Cyber Security Centre subsequently issued urgent guidance warning customers about targeted scams referencing the breach. Stealing information is only the first stage; the real danger is how that data is subsequently weaponized against the victims.

8. The Second Attack Happens After the Breach

Suppose someone stole the following information:

Email: john.smith@example.com
Phone: 07XXXXXXXXX
Postcode: M1 XXX
Vehicle: AB26 XYZ
Context: Manchester Airport parking customer

None of those fields is a password. None is a credit-card number.

But imagine receiving this message two months later:

Manchester Airport Parking

“Following the recent security incident, your vehicle AB26 XYZ has been identified among affected parking customers. Please verify your booking details to ensure your account remains protected.”

Now the criminal has several psychological advantages:

  • They know your exact registration.
  • They know which airport you use.
  • There really was a cyberattack.
  • And the message is referencing that real incident.

Suddenly the phishing message doesn't feel random. It feels personal.

This is precisely why MAG itself now advises affected customers to remain alert for suspicious emails, calls and text messages. MAG also states that it will not unexpectedly contact customers asking for payment-card details, banking information or passwords.

The Stolen Information Was Eventually Made Public

MAG's current incident guidance contains another important update. It tells customers who received an affected-customer notification that their information was made publicly available.

That changes the risk. A private criminal group possessing stolen information is one problem. Publicly available stolen information means potentially many different criminals can obtain it.

MAG breach
    ↓
Customer data stolen
    ↓
Information published
    ↓
Other criminals obtain it
    ↓
Victims profiled
    ↓
Targeted phishing / smishing / vishing
    ↓
Credentials or money stolen

The original cyberattack can therefore create opportunities for completely separate attacks months or even years later.

9. Did FulcrumSec Definitely Use the Exposed Iterable Keys?

This is where we need to remain careful. There are several things we can demonstrate:

  • MAG confirmed the breach.
  • MAG confirmed the affected categories of information.
  • FulcrumSec claimed responsibility.
  • FulcrumSec claimed that airport-specific Iterable credentials exposed in JavaScript provided access.
  • Scott Helme independently found three airport-specific Iterable credentials in MAG's JavaScript.
  • Historical archives indicate those credentials had been exposed since 2022.
  • Helme found Iterable-specific characteristics in breached records.

Those pieces fit together unusually well.

But MAG has not publicly released a forensic report saying: “This is definitively how the attacker obtained access.”

So I would describe the Iterable explanation as strongly supported by independent technical evidence, rather than officially confirmed. That distinction is important. Cybersecurity reporting becomes unreliable very quickly when an attacker claim is repeated by news outlets until it is accepted as uncontested fact.

10. Could a SOC Have Detected This?

Potentially. But this is also where the case becomes uncomfortable for defenders.

Imagine the attack happened broadly as FulcrumSec described:

An attacker obtains a legitimate API credential. They use it against Iterable. From Iterable's perspective, the requests may initially appear authenticated. MAG's laptops could be completely healthy. EDR might see nothing. There may be no malware, no suspicious executable, and no lateral movement through MAG's internal network.

Some of the most valuable telemetry could instead exist inside the SaaS provider's API logs.

[WHAT A DEFENDER WOULD NEED TO MONITOR IN SAAS API LOGS]
• Large numbers of customer records requested
• Bulk export operations triggered
• API calls originating from unusual IP addresses or hosting ASNs
• Requests arriving from unexpected countries
• Sudden volume increases against customer profiles
• Old credentials becoming unusually active
• Requests directed to rarely used administrative endpoints
• Abnormal outbound data transfers
• One credential being used concurrently from several locations

This is why modern SOC monitoring increasingly needs to extend beyond traditional endpoints and firewalls.

Your SaaS Platforms Are Part of Your Attack Surface

A modern company attack surface looks more like this:

                 AWS / Azure
                     |
Marketing SaaS ---- Company ---- Customer Portal
                     |
                    APIs
                     |
                  Suppliers

The organisation's information exists across all of those environments. Attackers don't particularly care which one contains the easiest route. If the endpoint is difficult to compromise but a third-party API exposes the same customer data, they'll attack the API.

Security architecture therefore has to follow the data, not simply the corporate network.

11. What Should Organisations Learn from MAG?

1. Treat frontend applications as public environments

Anything sent to the browser can potentially be inspected. Never assume minification, bundling or obscure filenames make a secret safe. They make it inconvenient to find. That isn't the same as secure.

2. Use client-side credentials for client-side applications

If a vendor provides separate browser and server credentials, there is usually a security reason. Server-side secrets should remain server-side.

3. Apply least privilege

Ask a simple question about every credential: “If somebody steals this tomorrow, what is the worst thing they can do with it?” If the answer is “Export our customer database,” that credential deserves considerably stronger protection.

4. Scan the application you actually deploy

Searching GitHub repositories for secrets is useful, but final production bundles matter too. Build processes can inject environment variables into compiled JavaScript. Scan production assets.

5. Rotate credentials

The MAG credentials identified by Helme appear to have remained unchanged for approximately four years. Credential rotation limits the useful lifetime of a leaked secret.

6. Monitor API behaviour

Authentication answers: “Does this request have a valid credential?” Security monitoring should also ask: “Does what this credential is doing make sense?” A legitimate credential exporting millions of records can still represent malicious activity.

7. Don't simply remove exposed secrets

If a credential appears publicly, removing it from the website is not enough. Assume somebody may already have copied it. Revoke it. Rotate it. Then investigate its historical use.

12. What Should Affected Customers Learn?

The practical advice is much simpler. Be cautious about unexpected messages connected with:

  • Manchester Airport, London Stansted, or East Midlands Airport
  • Airport parking, valet bookings, and lounge reservations
  • Fast Track passes
  • Refunds or flight disruption compensation
  • Booking verification checks
The Fundamental Defense Rule:

Correct personal information does not prove that a message is genuine.
If someone knows your registration number, that does not prove they're from the airport. If they know your postcode, that does not prove they're from MAG. Sometimes the reason a criminal knows those things is precisely because the information was stolen.

13. The Bigger Lesson

The Manchester Airports Group breach is interesting because it sits at the intersection of several problems that modern organisations face:

API security. SaaS security. Secret management. Third-party data. Frontend security. Credential lifecycle management.

And this isn't theoretical. Academic researchers have now demonstrated exposed API credentials across thousands of real webpages. T-Mobile has experienced unauthorised API access affecting tens of millions of customer accounts. Trello changed API behaviour after attackers abused email-based profile lookups at enormous scale.

MAG therefore shouldn't be viewed simply as “Another company got hacked.” It is a useful example of how the attack surface has changed.

Twenty years ago, security teams concentrated heavily on protecting the corporate network. Today, an organisation can have excellent endpoint security and still expose customer information through:

  • a SaaS integration,
  • an API,
  • a cloud configuration,
  • a forgotten credential,
  • or a JavaScript bundle downloaded by millions of ordinary visitors.

And perhaps the most uncomfortable part is that none of those things necessarily causes an application to stop working. Everything can continue functioning perfectly. Customers can make bookings. Marketing analytics can collect events. Developers can deploy new versions. Monitoring dashboards can stay green.

Until somebody asks a different question: What exactly did we just send to the browser?

14. What We Know (The Evidence Matrix)

CONFIRMED ✓ Primary Source Disclosures
  • MAG suffered a cybersecurity incident involving an unauthorised third party.
  • Information associated with airport Wi-Fi, parking, lounges and Fast Track was obtained.
  • Affected information included email addresses, phone numbers, postcodes and vehicle registrations.
  • Operational airport systems were not involved; passenger safety and aviation security were not compromised.
  • The affected system did not contain customer bank or payment details.
  • Affected customers have been informed, and MAG confirmed the information was made publicly available.
INDEPENDENTLY VERIFIED ✓ Forensic & Academic Research
  • Scott Helme identified three airport-specific Iterable credentials in publicly served JavaScript.
  • Archived copies indicate exposure beginning in June/July 2022 and continuing until August 2026.
  • Technical analysis found characteristics consistent with the stolen information having passed through Iterable.
  • Independent academic research published in 2026 demonstrates that publicly exposed web API credentials are a wider real-world problem, particularly in JavaScript environments.
CLAIMED ⚠ Attacker Statements
  • FulcrumSec claims responsibility for the MAG incident.
  • The group claims it used the exposed Iterable credentials.
  • It has made additional claims concerning the volume of information stolen.
  • These claims should remain attributed to FulcrumSec unless independently confirmed.
STILL UNKNOWN ? Unanswered Questions
  • The definitive initial-access vector has not been publicly confirmed by MAG.
  • The exact date on which attackers first accessed the information remains unclear.
  • The duration of attacker access has not been publicly established.
  • It is unknown whether anyone else discovered or abused the exposed credentials during their years of public exposure.
  • A complete public forensic report has not yet been released.

OWASP ZAP for Testing Your Own Web App

ZAP's own guide: active scanning is a real attack

You have built a website, a booking form, a customer portal or an internal tool. It works. But does it leak information in its headers? Does the login cookie lack basic protections? Could someone inject code through a search box? Automated scanners from strangers are already asking these questions. ZAP lets you ask them first, on your own terms.

Tool card What it is: a web application security scanner and intercepting proxy
Cost: free and open source
Runs on: Windows, macOS and Linux, and as a Docker container
Originally: an OWASP project, now developed by the ZAP team with backing from Checkmarx
Good for: finding common web vulnerabilities and misconfigurations in sites you own
Skill level: beginner for automated scans, advanced for manual testing

How ZAP Works

ZAP's Getting Started guide explains that at its core, ZAP is a "manipulator-in-the-middle proxy". It sits between your browser and the web application, so it can see, record and, if you want, change every request and response before passing it on.

That gives it three main ways of finding problems:

  • Spidering. ZAP crawls the site to discover its pages. The traditional spider follows links in the HTML; the client spider drives a real browser, which is slower but handles modern JavaScript-heavy apps better.
  • Passive scanning. ZAP examines all the traffic passing through it without changing anything. The guide describes it as safe: it does not alter responses in any way.
  • Active scanning. ZAP sends known attacks to the application to see how it responds, testing for issues such as injection and cross-site scripting. The guide is blunt: active scanning is a real attack on the target and can put it at risk.
Passive scanning watches. Active scanning attacks. Know which one you are running, and where.
Only test what you are allowed to test ZAP's guide says you should only use it to attack an application you have permission to test with an active attack. That means your own applications, or ones you have written authorisation for. Run active scans against a test or staging copy, not production: they can create junk records, send emails, trigger lockouts or crash fragile systems. If your site is hosted by someone else, check their rules on security testing too.

Running Your First Scan

  1. Download ZAP from zaproxy.org and start it.
  2. Practise on a deliberately vulnerable app first. OWASP Juice Shop is a popular training application full of intentional flaws, designed to be attacked. Run it locally and point ZAP at it.
  3. Use Automated Scan. On the Quick Start tab, click Automated Scan, enter the URL in "URL to attack", and click Attack. ZAP crawls the application, passively scans each page, then runs an active scan.
  4. Explore manually too. Choose Manual Explore to open a browser routed through ZAP, then click through your app, log in and use its features. Automated spiders miss pages behind logins and complex forms; manual exploring lets ZAP see them.
  5. Review the Alerts tab. Findings are grouped by risk level: High, Medium, Low and Informational.

A Safe Scan for Every Release: The Baseline

For routine checks, ZAP provides a packaged baseline scan that runs in Docker. According to ZAP's documentation, it runs the spider against the target for one minute by default, waits for passive scanning to finish and reports the results, without performing any attacks. ZAP describes it as ideal for CI/CD pipelines, even against production sites. 

docker run -t ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t https://www.example.com

Its exit codes let a build pipeline react: 0 for success, 1 if any check fails, 2 for warnings only. By default every finding is a warning, and a configuration file lets you promote important rules to failures or ignore ones that do not apply. Adding this to your deployment pipeline means every release gets a basic security check automatically.

Reading the Results

Your first scan will probably produce a long list. Do not panic. Typical findings, roughly from most to least urgent:

  • Injection and cross-site scripting. Reported by active scans when input is reflected or processed unsafely. Take these seriously and verify them first.
  • Cookie problems. Session cookies without the Secure, HttpOnly or SameSite flags, making them easier to steal or misuse.
  • Missing security headers, such as Content-Security-Policy, Strict-Transport-Security or anti-clickjacking headers.
  • Information disclosure. Error messages, server version numbers or comments revealing internal details.
  • Informational notes, which are context, not problems.

For each alert, ZAP shows the URL, the evidence, a description and a suggested fix. Verify before you act: automated scanners produce false positives, so reproduce the issue and check whether it is real in your application. Many findings map to categories in the OWASP Top 10, the widely used list of the most critical web application security risks, which is a good place to learn more about each one.

Limits to Keep in Mind

  • Automated scanners miss logic flaws. ZAP will not notice that one customer can view another's invoice by changing a number in the URL. Broken access control like this needs manual testing and code review.
  • Authentication is tricky. Scans that cannot log in only test the public pages. Configure authentication, or explore manually while logged in.
  • A clean report is not a security guarantee. It means ZAP found nothing it knows how to find.
  • It complements, not replaces, secure coding practices, dependency updates and, for important applications, professional penetration testing.

Final Thoughts

If you run a website, start with a baseline scan this week: it is passive, quick and safe. Fix the easy wins such as cookie flags and headers. Then set up a test copy of your application and try an automated active scan against that. Finding your own vulnerabilities is always cheaper than having someone else find them for you, as the breaches we cover every Friday show.

Attackers will test your web app for free. Make sure you got there first.

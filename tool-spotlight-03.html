Sysmon for Endpoint Visibility on Windows

Something suspicious happened on a Windows laptop yesterday. You open the event logs and find... very little. A logon, a service start, an update. What you really want to know is which program ran, what launched it, what command line it used, and where it connected. By default, Windows mostly does not record that. Sysmon does.

Tool card What it is: a Windows service and driver that logs detailed system activity to the Windows event log
Cost: free, from Microsoft Sysinternals
Runs on: Windows 11 and Windows Server 2019 or later (a Linux version also exists)
Works with: Event Viewer, Windows Event Forwarding, and SIEM tools such as Wazuh
Good for: investigating incidents, hunting for threats, writing detections
Skill level: intermediate

What Sysmon Does

System Monitor, or Sysmon, is part of Microsoft's free Sysinternals suite, written by Mark Russinovich and Thomas Garnier. Microsoft's documentation describes it as a Windows system service and device driver that stays resident across reboots to monitor and log system activity to the Windows event log.

Among the things it records, according to Microsoft:

  • Every process that starts, with its full command line, its parent process and a hash of the program file.
  • Network connections, linked to the process that made them, with addresses, ports and host names.
  • Drivers and DLLs loaded, with their signatures and hashes.
  • Files created, useful for watching download folders and startup locations.
  • Registry changes, including the autostart keys malware uses to survive reboots.
  • DNS queries, showing which process looked up which domain.
  • Attempts to read another process's memory, such as credential-stealing tools targeting LSASS.

It also starts logging early in the boot process, and runs as a protected process to resist tampering.

Microsoft is equally clear about what Sysmon does not do: it does not analyse the events it generates, and it does not try to hide itself from attackers. Sysmon is a camera, not a guard. Someone, or something, still has to watch the footage.

Antivirus asks "is this file bad?" Sysmon answers "what actually happened?"

Installing It Sensibly

  1. Download Sysmon from Microsoft's Sysinternals site, or use the built-in version if your Windows build has it (see below).
  2. Start from a community configuration, not the defaults. Without a configuration file, Sysmon logs process creation with SHA1 hashes but no network activity. Logging everything, on the other hand, produces an unmanageable flood. Well-maintained starting points include SwiftOnSecurity's sysmon-config, described as a configuration template with high-quality event tracing, and Olaf Hartong's more exhaustive sysmon-modular.
  3. Install from an administrator command prompt, for example: sysmon64 -accepteula -i sysmonconfig-export.xml. No reboot is needed.
  4. Find the logs in Event Viewer under Applications and Services Logs → Microsoft → Windows → Sysmon → Operational.
  5. Update the configuration later with sysmon64 -c newconfig.xml, and test changes on one machine before rolling them out.

Sysmon is coming into Windows itself. Microsoft began testing Sysmon as a built-in optional feature in Windows 11 Insider builds in February 2026. BleepingComputer reported that it is disabled by default, is enabled through Settings → System → Optional features → More Windows features (or with DISM), and requires any standalone Sysmon to be uninstalled first. Check whether your version of Windows includes it before downloading the standalone tool.

The Events Worth Learning First

  • Event ID 1, process creation. The most valuable event. Look for unusual parent-child pairs, such as Word or Excel starting PowerShell, or a command line full of encoded text.
  • Event ID 3, network connection. Which process is talking to the internet? A document viewer or a process in a temporary folder connecting out is worth a look.
  • Event ID 11, file created. New executables appearing in Downloads, Temp or Startup folders.
  • Event IDs 12 and 13, registry changes. New entries in Run keys and other autostart locations, a classic persistence technique.
  • Event ID 22, DNS query. Which process looked up which domain, ideal for tying strange lookups to a specific program.
  • Event ID 10, process access. Tools opening the LSASS process to steal credentials. Microsoft warns this can be noisy, so it should be filtered carefully.
  • Event ID 8, CreateRemoteThread. One process creating a thread inside another, a technique malware uses to inject code and hide.

Many of these are exactly the signals of "living off the land" attacks, where intruders use built-in Windows tools rather than malware, as covered in Threat of the Week, Episode 08.

Turning Logs Into Detection

On a single machine, Event Viewer and PowerShell's Get-WinEvent are enough to investigate. Across an organisation, you need the events in one place:

  • Collect centrally with Windows Event Forwarding or a SIEM agent. Logs that stay on a compromised machine can be deleted.
  • Write detections for the patterns that matter to you. Sigma rules, covered later this season, are a common way to describe Sysmon-based detections in a portable format.
  • Use it during incidents. When you isolate an infected machine, as in Playbook Monday, Episode 08, Sysmon's process and network history is often what tells you how it happened and what else it touched.
  • Combine it with network evidence. Sysmon tells you which process made a connection; a packet capture, as in Tool Spotlight, Episode 01, tells you what was in it.

Limits to Keep in Mind

  • Configuration is everything. Too little and you miss what matters; too much and the logs are ignored or overwhelm storage.
  • It does not alert or block on its own. You need something to read the logs.
  • A local administrator can stop or remove it. Forward logs off the machine, and alert when Sysmon stops reporting.
  • It is not a replacement for endpoint protection or EDR. It complements them, and many security teams use it alongside commercial tools.

Final Thoughts

Every incident investigation eventually asks the same questions: what ran, who started it, and where did it connect? Sysmon answers them, for free, on every Windows machine you install it on. Install it with a good community configuration on one machine this week, open the Operational log, and see what your computer has been doing.

You cannot investigate what you never recorded. Turn the camera on before you need the footage.
